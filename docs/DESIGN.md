# LumiAH design

LumiAH is an agent harness for Lumiverse. A main agent works in a loop with tools, sub-agents, sessions, a workspace and guidance files before each reply, in a process of its own beside Lumiverse: the runtime (§25). This document is the contract the code is built to. Where the code and this document disagree, one of them is wrong and gets fixed.

**What is built:** §1 to §8 and §11 to §29, with tests, except where a section says a part is not yet built. The README's "Things to know" lists the gaps a user can meet.

## 1. Parts and where they run

| Part | Source | Runs | Owns |
|---|---|---|---|
| Core | `src/core/` | Anywhere: it reaches the outside only through ports | The agent loop, the provider session, budgets, sessions and compaction, the tool, agent and skill registries, the workspace, jobs, the trace |
| Link | `src/link/` | Both ends | The contract between the runtime and the extension backend: envelopes, requests, pushes, versions; the asks' road through Lumiverse's proxy, the timing log, and the transport's settings |
| Runtime | `src/runtime/` | Its own process beside Lumiverse (`dist/lumiah.js`, under Bun) | The loopback endpoint Lumiverse calls, the link's client end, the agents' model calls to their providers on its own connections (§26), the core's documents and blobs on its own disk (§27), its copy of the chats and world books its runs read (§28), the core's other ports over the link, the turn, its own updates (§29) |
| Extension backend | `src/extension/backend/` | Lumiverse's extension worker (`dist/backend.js`) | The link's server end, tagging, the storage that mirrors the runtime's and which runtime holds it (§27), chat, lore and preset access, Lumiverse's events handed on to the runtime's copy (§28), anchors, settings, the live buffer |
| Host reads | `src/host/` | Both: the runtime and the extension backend | The read side of a chat's path and ranges, of lore and of the recall tools, over rows as Lumiverse's Spindle API gives them: the backend runs it over Spindle, the runtime over its copy (§28) |
| Extension frontend | `src/extension/frontend/` | The browser (`dist/frontend.js`) | All UI |
| Shared | `src/shared/` | Backend and frontend | The messages between the two, and types both read |

Rules that keep the boundary:
- **Core imports nothing outside `src/core/`.** No Lumiverse type, no Spindle call, no Node or Bun API beyond what both a worker and a process have (`crypto.subtle`, `AbortController`, timers). A test enforces it.
- **Only `src/extension/backend/spindle.ts` touches the `spindle` global.** Everything else in the backend talks to an interface it implements, so tests run against a fake.
- **The extension backend's bundle must pass Lumiverse's install scan:** no `eval`, no `Function(`, no `process.env`, no `node:` import, no `Buffer.from(…, "base64")`, no `fetch`, no `Bun.serve`. The runtime is an ordinary process and has no such limit, so what the scan would refuse lives there: nothing of `src/runtime/`, nor of the model layer it bundles (§26), reaches the backend's bundle.
- **`src/host/` reaches only the core and the link's plain code,** so the runtime and the backend read a chat and its lore with one logic, written once, that needs no Spindle, disk, database, socket or model library. A test follows every import from it.
- **A bundle holds the same code wherever it is built.** The build lists each bundle's inputs and fails, naming the file, when one lies outside the repository (Bun takes a package from any `node_modules` above the repository it doesn't find inside it). What the repository leaves uninstalled on purpose is named in the build: `supports-color`, which a library in the runtime asks for only to colour its own debug lines, and does without. The runtime's bundle is made with `--ignore-dce-annotations` (`scripts/bundle-flags.ts`): pi-ai loads each provider's API lazily and declares its modules free of side effects, so without it Bun's bundler left those modules unstarted for whatever imported them the plain way, and a function of pi-ai's called before any such API was used found its module's state missing (ending an agent's session threw on a runtime that hadn't yet called an Anthropic model). With it, the bundle starts its modules as the sources do unbundled.
- **Another extension uses LumiAH as a package.** It bundles the backend and frontend pieces into its own extension, ships the runtime beside them (§29), and registers its tools, agents, skills and guidance. LumiAH imports nothing from any extension that uses it.

## 2. One reply

1. The user sends a message in a chat whose connection is the loopback.
2. Lumiverse assembles the prompt from the active preset. The extension's prompt interceptor runs last, tags the generation with a single-use token tied to the chat and the generation, and leaves out the messages the user's history cutoff hides.
3. Lumiverse calls the loopback connection: `POST /v1/chat/completions` on the runtime, with the assembled messages, the sampling parameters and the tag.
4. The runtime checks the tag with the extension, which answers with the turn: the user, the chat, the generation and what kind it is (new reply, regenerate, swipe, continue), and the message it targets.
5. The runtime resumes the chat's session from the anchor on the chat's active path (§5) and runs the main agent (§3). Every model call an agent makes goes from the runtime straight to its provider, on one of the runtime's own connections (§26).
6. While the main agent works, its steps go to the reply's thinking block as progress lines and to the live session view in full.
7. The reply is written (§3.2) and streamed back to Lumiverse as the completion.
8. The runtime hands the turn's record to the extension, which writes the anchor on the reply's message once Lumiverse has saved it.

A request with no tag is not a turn. The runtime passes it as it came to the writer's connection, else to its default connection, so a feature of Lumiverse that happens to use the loopback connection still works. It goes whole or not at all: one that holds something the runtime's model calls can't carry (a speaker's name, a picture given by its address, a file, audio or video, a prefix the connection can't continue) is refused before anything of it is sent, in words that name it, never sent on without it (docs/RUNTIME.md, *A request with no tag*).

LumiAH answers only generations that reach the loopback connection. A chat on any other connection is untouched. Which connection a chat generates on is Lumiverse's to pick, and the extension follows the same order: the chat's own connection, else the one selected in Lumiverse, else the default, else the first listed. Where Lumiverse doesn't tell an extension which one is selected, the page reads it there and says it with `lah.hello`.

## 3. The main agent and the writer

### 3.1 The main agent
One continuous session per chat. It decides its own steps: there are no stages, and no code calls a tool or a model on its behalf. Each turn it is given:
- its instructions (an editable text) and the guidance files that apply;
- what it carries from earlier turns: the last compaction summary, and a receipt for each turn since;
- the request: the messages Lumiverse assembled, as a document it reads, with the preset's instruction blocks marked as the instructions the reply must achieve;
- where only the model's replies are the story (§24.4): that the user directs the story from outside it, and, where the setting gives it, the user's newest message as the direction for this reply, read from the chat itself.

It works with tools until it has what the reply needs, then calls `write_reply` with a brief.

### 3.2 The writer
By default a separate agent writes the prose. Its call is Lumiverse's assembled messages as they came, with the main agent's brief inserted, the request's own sampling parameters, and no tools, on the writer's connection (one of the runtime's, §26). Its answer streams to Lumiverse as the reply. So the user's preset governs the prose as it does without LumiAH: the messages it assembled, and each sampling parameter the writer's provider takes.

Who writes is a setting. The main agent may write the reply itself: then its final answer is the reply, and there is no second call.

Nothing of LumiAH's own that fails before the writer costs the reply. A main agent that stops short of a brief (a limit, a failed call), a session that can't be resumed, a summary that can't be stored, or settings that can't be read all end in the same place: the writer writes from the request alone, unless the setting `reply.withoutBrief` says such a turn fails, and the thinking block, the trace and the turn's record say what failed. A summary that fails only leaves the notes whole: the main agent still works. With settings that can't be read the main agent isn't run at all, and the writer's call goes to the runtime's default connection; no prompt or transcript is kept for that turn. A main agent that writes the reply itself has no writer to fall back on: its turn fails with why.

### 3.3 Everything here is a default
The main agent's and the writer's instructions, tools, connection, model, effort and budgets are settings the user can change. Every text sent to a model has an id and can be replaced by the user. Every limit is a setting with a default. A fixed value in the code needs a comment that says why it can't be a setting.

### 3.4 The reply, released by the agents
The reply may be written by the agents themselves, with no writer. `reply_write({text})` releases a passage: it streams to the user at once, after what was released before, and may be called any number of times in a turn. The reply is everything released, in order, and the turn's record holds it. An agent may hand the reply's stream on: `delegate` with `to_reply` (§14).
- **Who may release:** the run's main agent, and an agent whose definition the extension that builds LumiAH in supplies (a user's definition in its place counts), where its definition names `reply_write`. No agent holds it by default. A job's agents and a side session's never do: they write no reply.
- **A turn that released text needs no `write_reply`.** It ends when the main agent answers, and that answer is not added. Once text is released, `write_reply` is refused in words that say so: a writer would write a second reply after it.
- **Stop.** Once the turn is stopped nothing more counts as released: the reply and the record hold what reached the user before.
- **The extension's word on each passage** (§21): asked before a passage goes out, told once it did.
- **What the main agent is shown, and who writes,** may be the extension's to say for a chat it claims (§21): only the user's newest message in place of the whole request, and a reply that is only what its agents release.

## 4. Core

### 4.1 The loop
`startAgent(spec, deps)` returns a handle; `send(text)` runs the loop: call the model, run the tools it calls (as many at once as its budget allows), send the results back, until it answers or a limit stops it. It keeps:
- native tool calls, with a fallback that offers the tools as text when a connection refuses them, and recovery of tool calls a model writes as text;
- budgets per call, per agent and per turn (tokens in and out, rounds, time, revisions);
- a loop detector for the same call made on the same state, with the same result, several times running; the same call written more than once in one answer is run once, and of one answer's calls that would end the agent's work (`write_reply`) only the first is run;
- no call of a round begun once the turn was stopped or its time ran out;
- clipping of long tool results, with the whole kept for `scratch_read`: past *Tool results clipped past* (`loop.clipChars`), or past the length a tool says it gives whole (`wholeChars`, for a tool that bounds its own answer by a setting and is meant to be read in one go), where that is more; and, where *Prompt per call* limits an agent's prompt, a result that would take its next call past it is cut to the room left, in one editable line (`runtime.window_cut`), so the call is still made;
- one more go for a call its answer room cut while it was all thinking (no text and no whole tool call came of it): the call is made again once, with its room times *More room after a cut answer* (`loop.cutRoomFactor`, 2) up to *Most room after a cut answer* (`loop.cutRoomTokens`, 64,000), and the model is told in one editable line (`runtime.cut_thinking`) to think briefly and act. The first call counts against every budget and shows in the live view as cut; the second shows as the same step again. Cut so again, it ends as a cut answer does (a job fails in words that say so). An answer cut after it wrote text or a whole tool call is handled as any cut answer is;
- reasoning carried across tool calls where the provider needs it;
- a prompt cache for each agent's session, which its provider keeps as long as *Kept for* says (`cache.retention`: none, a few minutes, about an hour); the provider places its own breakpoints (§26);
- request and token throttles per connection.

A tool is `{ name, description, parameters, state?, wholeChars?, run(args, ctx) }`, with `parameters` a hand-written JSON Schema. Its outcome is `{ text, error?, end? }`; `end` finishes the send with that text.

### 4.2 Ports
Core reaches the world through one object, the host:

| Port | What it gives |
|---|---|
| `models` | One model call: messages (text, tool calls and tool results as parts), tools, effort, sampling parameters, a signal; the answer with its tool calls, reasoning and usage. Deltas as they arrive, for a call that streams |
| `connections` | The runtime's connections (§26): which exist, each one's provider and model, the default, and whether one takes several tool calls in an answer |
| `blobs` | Text stored once by its hash |
| `store` | Small JSON documents by path, written whole |
| `chat` | The chat's active path with each message's anchor; messages by range; an anchor written on a message |
| `lore` | The world books that apply to a chat, their entries, and the entries Lumiverse activated for this generation |
| `preset` | The active preset's blocks, in order, each with its role and whether it is an instruction or a marker |
| `trace` | Where every step of every agent goes |
| `clock`, `log` | Time and diagnostics |

The runtime implements the host: `models` and `connections` with its model layer (§26), `store` and `blobs` on its own disk (§27), the reads of `chat` and `lore` from its copy of them where the copy can vouch for its answer (§28), the rest over the link. Tests implement it in memory.

### 4.3 Base tools
Search, grep and read over the chat; an index, search, grep and read over lore; the preset's instruction blocks; the lore activated for this turn; `past_turn` for an earlier turn's work in full; `scratch_read`; `write_reply`; `reply_write` (§3.4). Later: workspace tools, delegation, scheduling, summarize, MCP tools.

Tool results follow one set of conventions: results are paged with a cursor, a search says how many it found and how many it shows, an error says what to do next, and nothing returns more than its limit setting allows.

## 5. Sessions and anchors

A session is the main agent's working memory across turns: what it was told, what it called, what came back, what it concluded. The chat's own messages are not copied into it; Lumiverse sends those with every request.

- **Each turn ends with a record** on the reply's message, in that message's extension metadata under LumiAH's key, one per swipe: the hash of the turn's session segment, of a compaction summary when one was made, of the turn's transcript, and a path hash chained over the messages before it.
- **A deleted swipe** moves the later swipes' records down with them, and with them the place of a record still to be written. A record whose own swipe was deleted is written nowhere.
- **Bodies are blobs,** stored once by hash and never changed.
- **The session at a turn** is read by walking the chat's active path back to the latest record with a summary, then taking the segments after it. A swipe, a regenerate, an edit and a branch therefore need no bookkeeping: whatever path is active is the one that is read.
- **What the main agent carries of a turn since is a receipt:** each thing it did in a line or two, with the start of each call's arguments and of each result, each within its own length setting, and how to read either whole (`past_turn`). A file it wrote or a long brief is never carried whole in the notes of the turns after.
- **A record whose path hash no longer matches** the messages before it (an earlier message was edited or deleted) is off the path. It is not used, and the main agent is told its notes from that point were dropped.
- **Compaction** runs when the session passes its token setting: the span is summarized, the summary lands with the turn's record, and the replaced span is kept so a rollback can restore it.
- **A summary lands only when its call ended of itself.** Whether it was cut is told from the call's finish reason, never from its last word.
- **A rollback** marks the summary's record, and the session then reads past it. The notes aren't summarized again until they have grown by `session.rollbackMarginTokens` or the user asks. A regenerate, a swipe or a continue of the reply the summary was made on carries the marked summary on its own record, so the rollback holds whichever swipe the chat shows afterwards. Only the first turn that reads past it is told (the main agent's message, and the session's line on the live view), as dropped notes are told once: no record on the path made since the rollback says no turn has read past it yet. The turns after go on reading past it with nothing more said, until a summary stands again.
- **An extension with its own per-message record** supplies the anchor itself, so a turn has one record and not two.

## 6. Link

The runtime is a client of Lumiverse like any other: it signs in as the user, finds the extension, opens the event socket, and sends the extension enveloped requests, each answered by its id. The extension pushes to the runtime's session.

**The runtime is required, and nothing stands in for it.** Every chat switched on is answered in the runtime (§25). While the runtime isn't linked (stopped, crashed, refused for its link version, forgotten), those chats' replies fail on the loopback connection, as a reply on any connection that doesn't answer does. LumiAH tells the user instead. A toast says so as a reply is about to go to a runtime that isn't linked; the chat's view says the runtime isn't answering (`ChatView.away`); and a reply the runtime itself has to refuse says why, and that nothing answers in its place. A mounting extension reads the same state for its own pages (`Backend.runtimeState`, `onRuntime`).

- **Versioned.** Both ends say their link version in `hello`, and this one is 2. A mismatch is refused in plain words that name which side to update, and a runtime refused for its version is still offered the extension's own build of the runtime (§29), so one that updates itself mends the link.
- **Three secrets, three jobs.** The runtime's Lumiverse session lets it reach the extension. The relay secret, minted when a runtime registers, tells that runtime's requests from a page's and from another runtime's; registering needs only the user's session, so it proves a runtime the account registered and no more. The loopback key, which the user puts in the connection, proves a completion request comes from that user's Lumiverse. The extension stores only hashes of the last two.
- **Streams are numbered.** What takes its time in the extension is answered on a stream: a tool that runs there (`tool.call`) and a tool call held for the user's word (`approval.ask`). A stream carries one chunk, its outcome, as a `chunk` push numbered 1: `value` or `error`. The extension keeps it until the runtime acknowledges it (`stream.ack`), and sends it again to a runtime that reconnected (`hello` names the streams the runtime still reads). The runtime gives a stream up before that with `stream.cancel`, when its caller no longer wants the answer. No model call crosses the link: the runtime makes its own (§26).
- **What a stream carries.** The `value` is the tool's `{ text, error? }`, or the user's answer, exactly as the page gave it (the core reads it, and runs the call only on a word that is exactly an approval, §17). On a stream the answer survives a reconnect, and the runtime can give it up like a call: it cancels the stream when the run stops or the wait runs out, which takes a held call down.
- **Patient streams.** The runtime gives up a stream that brings nothing for *Stream stalled after* (`runtime.stallMs`, 30 minutes). A held call waits on a person, so its stream is patient: silence is no stall. It ends early only when the extension stays out of reach (`runtime.lostMs`, 2 minutes) or no longer holds it.
- **Waits for the link.** A request the runtime makes while its link is down waits for the link to come up, and no longer than it was told: those of a reply, a job, a side session, a tool and a held call, and the runtime's own (`trace.push`, `settings.get`, `stream.cancel`, `setup.connection`), wait *Extension lost after* (`runtime.lostMs`, 2 minutes); the connection's model list and the key check of a request passed through (`models`) wait *Model list wait* (`runtime.modelsWaitMs`, 10 seconds). Once sent, a request waits *Request wait* (`runtime.requestMs`, a minute) for its answer. A wait that runs out fails as a timeout in words that name its setting and where it is changed (`WaitError`), and the reply, the tool's result or the log says them as they are; a problem no wait mends (the session ended, the extension missing, the link refused) fails at once.
- **The runtime asks, the extension answers.** Every request but `register` carries the relay secret, and every answer says how long the extension worked on it (`took`), for the runtime's timing log.
  - *The link itself:* `register` (`up` registers a runtime: the extension mints its relay secret and says which model its loopback connection names; set up again, a runtime that shows the secret it holds keeps its registration, so it goes on answering until `up` restarts it), `hello` (on every socket: both versions, the streams to resume, the settings' revision, what the extension supplies to the core and who the backend is, §21; the runtime's working copy and whether it asks to hold the mirror, answered with the extension's word on who holds it, §27; and what the runtime's copy of chat and lore may read, §28), `ping` (the heartbeat, naming the streams the runtime reads and the runs it works on: a stream the extension no longer holds ends at once, and a run the runtime no longer names is over; the answer counts the numbered pushes sent, so one lost on the way shows, §28), `mirror.release` (a runtime that stops cleanly lets the mirror go, §27).
  - *A reply:* `models` (the connection's model list and its Test, and a request passed through: whether the key is the user's loopback key), `turn.begin` (check and spend a tag, answered with the turn), `turn.commit` (the turn's record, written on the reply's message once Lumiverse has saved it).
  - *Tools:* `tools.list` (the tools that run in the extension, as they stand for a chat: the extension's own, and those of the MCP servers the user switched on, §13 and §16), `tool.call` (runs one), `approval.ask` (holds a call for the user's word, §17), and for any stream `stream.ack` and `stream.cancel`.
  - *Storage* (the mirror of the runtime's own store, §27): `blob.get`, `blob.put`, `doc.get`, `doc.put`, `doc.remove`, `doc.list` (the path of every document under a prefix); and for upkeep (§20) `blob.list` (every blob stored, a page at a time) and `blob.remove`. A write from the runtime's working copy names the process that holds the mirror (`mirror`), and the extension refuses it for good (`conflict`) from any other.
  - *The chat:* `chat.path` (the active path, each message with its anchor) and `chat.messages` (messages by range, with their text), for a runtime with no copy of the chat to read (§28); `chat.info` (the chat itself: its name, its character, the chat it was branched from), `chat.anchor` (a record rewritten later, as a rollback does), `chat.anchors` (every record LumiAH holds in every chat of the user's, a page at a time, for upkeep).
  - *What a run reads:* `lore.books` and `lore.entries` (as for the chat, where the runtime has no copy), `lore.activated`, `preset.blocks`, and `settings.get` (the settings, the user's texts, and their own definitions as stored, §13).
  - *For the pages:* `trace.push` (trace events in batches, for the live buffer), `job.changed` (a job was queued, began, was paused or resumed, or ended: for the pages' lists and the user's notices, §15), `ask.answer` (what the runtime answered to an `ask` push), `setup.connection` (what became of a `connection` push).
  - *What the lore and history tools read (§23, §24):* `recall.lore.read` and `recall.lore.activated` (the chat's books with each entry as Lumiverse keeps it, and what Lumiverse activated for a generation, with how), `recall.chat.messages` (messages with when each was sent), `recall.embedder` and `recall.embed` (the user's embedding connection, and vectors from it), `recall.memory.enabled`, `.search`, `.entity`, `.entities` and `.arcs` (Lumiverse's own memory of a chat), `recall.databanks.list`, `.documents` and `.content`, `recall.web.enabled` and `.search` (the user's own web search), and `book.read` (the chat's LumiBooks book). A runtime linked to a backend from before these falls back to the older requests, or reads the thing as not set up.
  - *The runtime's copy of chat and lore (§28):* `host.read` (one read of the extension's own chat or lore host, for the runtime's own user, where the copy can't vouch for its answer), `own.read` (the records an extension LumiAH is built into keeps elsewhere than on the messages) and `turn.lore` (the persona and the World Info entries of the chat's latest generation LumiAH heard, and the lists of world books the chat's lore is read with: every chat's, the active persona's, that generation's persona's, and the books of the character the runtime names with `character`, so none of the lists crosses on its own; a backend from before the lists gives none, and the runtime asks each over `host.read` as it needs it).
  - *The extension LumiAH is built into:* `extension.call` (one member of what it supplies to the core, run in its backend, §21).

  One thing crosses with no id, no secret and no answer: the `trace.deltas` notice, a model's answer as it arrives, for the live view. One that is lost is not sent again.
- **The extension tells the runtime,** in pushes: `chunk` (a stream's one chunk); `stop` (the user pressed Stop on a run; `by` says where, in the live view or in Lumiverse); `settings` (they changed: read them again before the next run); `secret` (a new relay secret, when the user rotates it on the Runtime page); `connection` (a loopback key to put in the user's loopback connection, making the connection when there is none); `ask` (something a page asked that the core does where it runs); `update` (the extension's own build of the runtime, offered to a runtime on another build, §29); `greet` (the extension's worker started anew: a runtime says hello now, not at its next ping); `mirror` (who holds the mirror changed for this runtime, or, to the one that holds it, what another runtime changed in the storage, §27); and, numbered together for each runtime, `event` (one of Lumiverse's events about the user's chats and world books), `own` (a mounting extension's records on a chat changed) and `copy` (what the copy may read changed), §28. Spindle gives an extension no way to make a connection, so the runtime does it with its own Lumiverse session, says what it did, and never keeps the key. It gives none to stop a reply either. A reply stopped from the live view is one Lumiverse still generates, so the runtime asks Lumiverse to stop it as its own Stop button does, and ends the reply itself when Lumiverse can't be asked or doesn't answer within *Wait for Lumiverse's Stop* (`runtime.stopAskMs`, 5 seconds).
- **What a page asks of the core is done in the runtime,** the only place the core runs: it keeps the workspace, the jobs, the side sessions and the spend (§27). The extension sends what a page asks of it (a file read or written, a job started, a list read) on as an `ask` (`{ ask, op, args }`), and the runtime does it with its core and answers: the core's own answer, or a refusal with one of the pages' error codes and words the page shows. `op` is a `group.method` of the harness from a fixed list (`src/link/work.ts`), or one of the runtime's own: its connections and sign-ins (§26), its store (§27), its copy of chat and lore (§28), how it is run and its update (§29), and its timing log. Nothing else can be reached. About a chat, the ask goes to the runtime that chat generates on (the one whose loopback connection it is on); about no chat, to the user's runtime heard from last; a page that names a runtime (`relay`) asks that one, and only ever one of the user's own. With none linked, the page is told so, with what to do.
- **Two roads for an ask.** Over the link an ask is an `ask` push, answered with `ask.answer`. Where it can, the extension sends it through Lumiverse's own proxy instead (`spindle.cors`), to the runtime's loopback server (`POST /x/ask`, `src/link/road.ts`), where it doesn't wait behind the link's large frames. That road is taken only while the extension holds the permission `cors_proxy`, the runtime says it listens on a loopback address, and that address has answered a probe through the proxy, since the runtime last opened its link, with a proof bound to the relay secret (a nonce goes out with no secret, and an HMAC of it under the secret comes back); and only for an ask whose wait fits under the proxy's 30 seconds and whose body fits in what the proxy carries. An ask on that road carries the relay secret as a bearer; to anything without it the runtime answers only a probe, and refuses the rest in fixed words. Past *Proxy road wait* (`pages.proxyMs`, 10 seconds) the ask is sent over the link as well, and whichever answers first is taken; one the road fails, or whose answer is too large for the proxy (25 MiB), goes over the link once. The runtime does an ask once by its id, whichever road brings it. A road that failed carries nothing for two minutes, then is checked again.
- **The timing log.** Each end keeps its latest 2,000 crossings in memory, and of each only the op, the road, the characters each way, the whole time, how long the other end worked on it (`took`) and how it ended: never what crossed. The extension's end logs the asks it sends, the runtime's end the requests it sends the extension. The Runtime page's Timings reads both (§8).
- **The work runner** (`src/link/work.ts`) runs what isn't a reply, in the runtime.
  - *Jobs.* The core queues a job and says so through its `jobs` port. A `now` job starts at once. An `after_reply` job starts once a reply turn of its chat has returned, however that turn ended. The core decides the rest: how many run at once, each job's budget, the day's tokens, whether its turn is still on the chat's path.
  - *Side sessions.* When a page says something in a side session, its next turn starts. One turn of a session runs at a time.
  - *Stop, say, pause.* A `stop` push ends a job's run or a side session's turn as it ends a reply's. What the user says to a run, and a pause or a resume of it (§18), arrive as asks.
  - *The hold.* While the user holds all jobs (`jobs.paused`, off by default), every running job waits at its agents' next round, and a job that begins waits at its first.
  - *After a restart.* A process that stops ends every run it had. Once the runtime has linked again, the runner has the core mark the jobs the restart cut off as interrupted, tells the pages of each, and takes up the ones still queued.
- **A deleted chat is forgotten where the core runs.** When Lumiverse says a chat was deleted, the extension keeps its id in the user's storage (`forget.json`) and asks the user's runtime to forget it (`chats.forget`, an ask): at once where one is linked, again whenever a runtime links, and, after a refusal (a reply under way in the chat), at that user's next ping. The id is let go once a runtime has answered (§20).
- **An extension's members are requests.** What an extension that builds LumiAH in supplies to the core (§21) runs in its backend. So the runtime hands the core a `HarnessExtension` whose every member is an `extension.call` (`linkExtension` in `src/runtime/host.ts`). `hello` says which members the backend has; one it lacks is answered in the runtime as not supplied, with no request. A member that reads (the definitions, a claim, the writer's request) is asked again after a socket that closed under it. A hook is sent once, so the extension never hears one twice.
- **One runtime for every extension.** The runtime bundle therefore holds no extension's code: it is the same whichever extension ships it. It links to the extension its command line names (`lumiah up --extension <identifier>`; LumiAH's own when none is named), and the backend says the rest on `register` and `hello`: the name its pages show, what to call the loopback connection, and where its Settings are shown (`settingsAt`, §7), which the runtime's own timeouts name. The loopback model follows from the identifier (`lumiah` for LumiAH itself, `lumiah-<identifier>` for an extension it is built into), so a user with both has two connections, and neither runtime takes the other's for its own.

## 7. Extension backend

- Registers the prompt interceptor, at the highest priority, so it sees the prompt as it will be sent. It is never registered as required: Lumiverse passes over an interceptor that fails or runs out of its time and sends the prompt as the one before left it, so nothing LumiAH does can cost a chat its reply. An interceptor can change the prompt or leave it, and no more: it can't stop the generation it works on. What LumiAH didn't make goes back to Lumiverse exactly as it came, the very messages with Lumiverse's own fields on them, so an interceptor that runs after it (a second backend made of LumiAH's code among them, §21) reads the prompt as Lumiverse made it. What it does with a prompt:
  - *On the backend's own loopback connection:* a chat switched on. It tags the turn (§2) and leaves out the messages the history cutoff hides.
  - *Any other prompt* it leaves exactly as it came. It holds no chat up to find out which this is: what it can't check within `tags.checkMs` counts as not LumiAH's.
- Serves the link: each request of §6 is checked against the contract, authenticated by its relay secret and answered once. `tools.list` and `tool.call` go to the extension's own tools and the MCP tools; `approval.ask` to the held calls; `extension.call` to what a mounting extension supplies; `blob.*` and `doc.*` to user storage, the mirror of the runtime's store (§27), which nothing else writes under `docs/` and `blobs/`, a working copy's write taken only from the runtime that holds the mirror (`mirror.ts`); `chat.info` and `chat.anchors` to the chat; `recall.*` and `book.read` to what the lore and history tools read (`recall.ts`); `host.read`, `own.read` and `turn.lore` to what the runtime's copy asks (`copy.ts`, §28); `job.changed` to the jobs; `ask.answer` to the asks. `hello` also says what the extension supplies to the core, who the backend is, who holds the mirror and what the copy may read.
- Makes no model call. The agents' calls go from the runtime to their providers (§26). The backend says only whether a key is the user's loopback key (`models`), for the connection's model list and for a request passed through.
- Writes each turn's anchor when Lumiverse saves the reply.
- Hands Lumiverse's events about a user's chats and world books (`COPY_EVENTS` in `src/link/contract.ts`) to that user's runtimes and no one else's, as it heard them, numbered for each runtime (§28). One that names no user goes nowhere.
- Keeps the live buffer: the latest run of each stream, sent to every page that has that stream's live view open. A stream is what a page follows: a chat's reply turns under the chat's id, a job's run under the job's id, a side session's turns under the session's id. A reply's run begins when its tag is spent; a job's run and a side session's turn begin when the runtime starts them, so their view starts from their first trace event. A run that failed says why in a sentence and, where a page can act on it, as a code beside the sentence (`cause`: the main agent's model can't call tools, a permission LumiAH needs is missing, one of the user's limits was reached). The code is read from the run's own trace (`cause.ts`), so a stored transcript says the same.
- Passes on Stop. Lumiverse's own Stop, and Stop on a page for any run (a reply, a job, a side session's turn), reach the runtime as a `stop` push that says where it was pressed. The run's tool calls under way here end with it.
- Keeps settings and the user's texts in user storage, and the user's own definitions with them: their agents and skills, what they switched off, and the MCP servers they switched on. One revision covers all of it, so the runtime reads whatever changed before its next run. Whether a tool's calls run or wait for the user, by tier and by tool (§17), is a setting too.
- Sends what a page asks of the core to the runtime (§6, `asks.ts`), through Lumiverse's proxy where that road reaches it, else over the link (§6). About a run under way: the runtime that runs it. About a job: the runtime it runs in while it isn't over, and its chat's once it is. About a side session: the runtime of the chat it is about. About a chat: the runtime whose loopback connection the chat is on. About no chat (the user's own workspace area, spend, the Agents page's lists, upkeep): the user's runtime heard from last. A page waits `pages.askMs` for it; what takes as long as the store is big is waited for over the link while the runtime stays linked. Where none is linked, or the one asked goes away or doesn't answer, the page gets `unavailable` in words that say what to do. Two runtimes linked for one user and one extension share the extension's storage, only one of them through a working copy (§27), and each counts the day's spend caps from what it spent itself.
- Holds the tool calls that wait for the user's word (§17). The held calls are part of the state every page holds, so the user answers on whichever page is open. A call stops waiting when it is answered, when the runtime gives it up (its run stopped, or the core's wait ran out), or when its run is over. Nothing of it is stored: a call can only wait while its run does. What an answer "for this chat" stands for from then on is the core's to keep.
- Keeps the jobs as the pages hear of them: the jobs not yet over, from each `job.changed`, and a notice when a job finishes, fails, is interrupted by a restart of the runtime, leaves the chat's path, or waits on the user's word. A notice is kept in user storage until the user dismisses it, so it is there on the next page they open; past `pages.noticesKept` the oldest go first. The user's two switches over all jobs are settings: off is the core's, and the hold is `jobs.paused`, which the runtime's work runner reads (§6).
- Lists and calls MCP tools through Lumiverse (`spindle.mcp`), which holds the connections and applies its own rules on what a server may reach; LumiAH never sees where a server is or what secrets it takes. It needs the `mcp_servers` permission: without it, or on a Lumiverse with no MCP, there are no servers and no MCP tools. A server offers nothing to agents until the user switches it on for them (§16). Each tool is then named `mcp:<server>:<tool>` with the tier `external`, where `<server>` is the server's name made safe for a tool's name (lowercase letters, digits and `-`; where two names come to the same, the server made later takes a number). `mcp:<server>` in an agent definition names every tool of that server. One call may take `mcp.callMs`; past it the call is given up in words that name the setting. A server that is on but can't be reached offers no tools and says why on the Agents page; it never takes a run's other tools away.
- Asks Lumiverse for as little as it needs. It can't work without five permissions: `interceptor` (to see a reply's prompt before it is sent), `chats` (to read a chat and switch itself on for it), `generation` (to hear when a reply starts, ends or is stopped), `chat_mutation` (Lumiverse puts reading a chat's messages under it, not only changing them; with it LumiAH also writes each reply's record) and `generation_parameters` (to tag the replies its runtime answers). Without any one of them no chat can be switched on, and the pages say which is missing and what it is for. Every other is optional: without one, the part it serves is quietly absent, nothing fails, and the pages list it as information, with what granting it adds. Several, `cors_proxy` among them, are ones Lumiverse lets only an owner or an admin grant, and an update of the extension never grants one it newly asks for.

  | Permission | Without it |
  |---|---|
  | `world_books` | the lore tools find no books |
  | `presets` | the agents know the preset only by the prompt it made |
  | `characters` | the world books attached to the chat's character aren't found, and guidance for a character isn't matched |
  | `personas` | the world book attached to the persona isn't found |
  | `mcp_servers` | no MCP tools |
  | `embeddings` | search is by word, not by meaning |
  | `memories` | the tools that read Lumiverse's memory aren't offered |
  | `databanks` | the databank tools aren't offered |
  | `web_search` | `web_search` isn't offered |
  | `cors_proxy` | the pages' asks, and a mounting extension's, reach the runtime over the link alone, never through Lumiverse's proxy (§6) |

- Is put together by `createBackend(host, env, options)`. `env` is the clock and the build (`now`, `later`, `build`) and, where the build ships the runtime beside the backend, that file's sha256 and size (`runtime`), which the backend offers a runtime on another build (§29). LumiAH's own backend gives no options. An extension that builds LumiAH in (§21) gives what it has of:
  - `identity`: who the backend is in Lumiverse. Its identifier (what its runtime links to), the name its pages and its runtime's words show, the name of its loopback connection, where LumiAH's records sit in its entry on a message, and where its Settings are shown when that isn't "<name>'s Settings" (`settingsAt`, as LumiRPEngine's Harness tab shows them): every timeout's words name that place, the runtime's own included.
  - `extension`: what it supplies to the core. Its agent definitions and skills, the chats it claims, the writer's request rewritten, and its hooks around a run.
  - `tools`: its own tools, listed beside the MCP tools and run here. One that takes an MCP tool's name stands over it.
  - `anchor`: where LumiAH's record sits in the extension's own record of a message (§5).
  - `declined`: the permissions it chose not to ask Lumiverse for (LumiRPEngine asks for no `characters`). LumiAH's pages never bring those up; what they serve is absent, as above.
  - `ownSwitch`: its own pages switch a chat on and off (LumiRPEngine's do). LumiAH's pages then offer no switch of their own, and say where it is (`RuntimeView.switchedBy`).
  - `withoutAgents`: built-in agents it leaves out (LumiRPEngine leaves out the chronicler and the story reader). They aren't listed, offered or started, and what only they do is off.
  - `ownElsewhere`: where it keeps LumiAH's record of a message elsewhere than on the message (LumiRPEngine's ledger): a reader of a chat's records, and a way to say they changed, which the runtime's copy reads and hears (§28).
  - `declinesLore`: it gives LumiAH no lore (LumiRPEngine's host answers none), so the runtime's copy keeps none either.

  Everything of a mounting extension runs in its backend; the runtime only asks (§6). A backend serves every user where the core's host serves one, so each member is the core's own with the user's id passed last.

- Answers only its own chats. With LumiAH and an extension that has it built in both installed, each has its own registry, loopback connection, records (§5) and switch. A chat switched on in one carries that backend's mark in the chat's metadata (`lumiah_chat_<identifier>`: the chat it was made on, the backend's name, since when, and the connection the chat had before the pin). The other backend reads the mark: it shows the chat as that one's, refuses to switch it on beside it, and leaves its prompts alone. A mark names its chat, so one copied along with a branch marks nothing there. A chat that generates on another backend's loopback connection counts as that backend's the same way.
- Takes a chat over at the user's word (`lah.chat.takeover`; the page asks them first). The other backend's mark is removed, a pin to that backend's loopback connection gives way to the connection its mark names (to none where it names none), and the chat is switched on here, pinned to this backend's loopback connection. Nothing asks the other backend, so this works whether or not that extension is still installed: a mark left by one that was uninstalled locks no chat out.
- Keeps every account's bookkeeping its own. The interceptor's turns, verdicts and waiting records, the live buffer's runs, the frames coming in parts, the streams and the jobs the pages hear of are held per account, and an account's settings trim only its own. What bounds the worker all accounts share is fixed (`CEILINGS` in `src/link/settings.ts`): each such setting has a ceiling no account can raise past, and a total across accounts, past which the account that holds the most gives up its oldest or the newcomer is told the extension is busy. A link request that names a chat is served only for a chat of the calling account's, a mounting extension's tools and members included.
- Has no last word. Lumiverse stops an extension's worker (a restart, an update, a disable, an uninstall) with no call the extension could act on, so nothing is undone then: a chat switched on stays pinned to the loopback connection, and the marks stay on the chats. What must outlive the worker is kept in the user's storage (a runtime's turn whose record is still to come, a deleted chat no runtime has forgotten yet, which runtime holds the mirror, the operator's switch of the database reader), and what a user should undo before disabling or uninstalling is in `docs/RUNTIME.md`. A worker started anew asks every runtime linked to it to say hello at once (`greet`, §6).

The transport settings this document names (`src/link/settings.ts`, the `transport` section of the user's settings). Each wait among them is also a row of the Timeouts page (§8), and a timeout says its setting's name and where to change it.

## 8. Frontend

One drawer tab. Every surface works at phone width (360 px) and uses the room on a desktop; no control depends on hover; touch targets are at least 42 px on a coarse pointer.

- **Live:** the session view. The main agent and every other agent as they run: what each was told, each answer with its thinking where the model gives it, each tool call with its arguments and result, each stop. Tokens, time and cost per call, agent and turn. The exact prompt of any call. Stop. Search, filter, copy and export. On a long transcript *Back to top* stands beside *Jump to the newest*, at phone width too.
- **Sessions:** a chat's turns, each with its transcript; compaction points; rollback.
- **Settings:** agents (connection, one of the runtime's: a picker lists the connections of the runtime that plays the open chat, else of the runtime heard from last, and says whose; model, effort, budgets, tools), every text, the history cutoff, who writes the reply. **Timeouts** holds every wait a user can meet, in five groups (waiting for the runtime, the link, tools and approvals, a model call, the copy and the store), each with its default; a timeout's words name its setting and this page (where a mounting extension shows LumiAH's Settings, they name that place, `settingsAt`).
- **Runtime:** each runtime registered, whether it is linked, which build it is, and which road the pages' asks take to it (§6), with what granting `cors_proxy` adds while it isn't granted; first-time setup, step by step; the loopback key; the runtime's connections and sign-ins (§26); for each linked runtime, its store (§27), its copy of chat and lore, *Chat data*, with the database reader's switch shown to the operator alone (§28), its update and how it is run (§29); *Timings*, from both ends' logs (§6): for each op and road how many crossed, the median, 95th percentile and slowest time, the time waiting against the time working, the largest each way, and the slowest of the latest; which chats LumiAH answers.

## 9. Conventions

- TypeScript, strict. No `any` without a comment that says why.
- JSON Schemas are written by hand. No schema library.
- A comment says why, not what.
- Prompts are texts with ids in one place per area, never string literals at a call site.
- Tests are `bun:test`, beside nothing: they live under `test/`, mirroring `src/`. A test checks behaviour a user or a caller would notice. Fixtures are synthetic.
- No file under `src/` knows about a particular extension that uses LumiAH.

## 11. The workspace

The workspace is the agents' only file system: markdown and other text files they keep for themselves and for each other.

- **Three areas.**
  - The chat's area (`/`) follows the story path, like the session.
  - `learned/` is kept with the chat itself: a swipe or an edit never changes it, and a branch copies it.
  - `~/` is the user's own area, shared by all their chats.
- **Storage.** A file's body is a blob. An area is an index: path to hash, size, when it was last written and by whom (an agent's id, a job's, or the user).
- **Anchoring.** Each turn's record holds the hash of the chat area's index as it stood when the turn ended. The chat area at a turn is the index of the latest record on the active path, plus what jobs on that path wrote since (§15).
- **Versioned writes.** A write or an edit names the hash of the version it was based on, or says the file is new. A mismatch is refused with the current hash, so the agent reads again. That is what lets the main agent, sub-agents and jobs work on the same files.
- **History.** The difference between two records' indexes is a turn's change set. The page shows a file's history, compares two versions and restores one.
- **Tools.** `workspace_list`, `workspace_read`, `workspace_grep`, `workspace_write`, `workspace_edit` (replace an exact match), `workspace_move`, `workspace_delete`, `workspace_pin` (a pinned file is put in the agent's context each turn, under a size setting).
- **Pins.** An agent pins in the chat's two areas, `/` and `learned/`. A pin in `~/` puts the file in that agent's context in every chat, so it is the user's to set and to lift, on the Workspace page, unless a setting lets agents (off as shipped); `workspace_pin` says so when it refuses.
- **Bounds.** A path is checked and normalized; one that leaves its area is refused. Nothing reaches the host's disk. File size, file count and total size have settings.
- **The user** reads and edits every file on the page. A user's edit is a versioned write like any other, recorded as the user's. An edit to the chat's own area goes to the area at the newest reply and beneath it as well (the area that reply's turn started from), so a regenerate or a swipe of the newest reply keeps it, as do the turns after it; the records it went beside are written again with their areas, so a branch cut there has it too. A swipe of the newest reply made before the edit keeps the files it had. (A job the user starts to write the chat's area is kept the same way, §22.)

## 12. Guidance

A guidance file is markdown an agent is given as part of its instructions, every turn.

- **Three levels:** the user's (`~/GUIDANCE.md`), a middle level (for a plain chat, the character's; an extension may name its own, such as a world's), and the chat's (`learned/GUIDANCE.md`).
- **Loaded** into every agent's system prompt in that order, under a size setting, with each level named so an agent knows whose words they are. The writer is given none (§3.2): the main agent carries what matters into its brief. A setting, off by default, puts the guidance beside the brief in the writer's request.
- **Edited** by the user on the page. An agent may edit the chat's level when a setting allows.

## 13. Agents, skills and tools as definitions

- **An agent definition:** id, name, description (what a delegating agent reads when choosing), instructions, tools (by name or family), connection, model, effort, budgets, and what it is given (the whole request, or only its task).
- **A skill:** id, name, description and a markdown body: a procedure an agent may follow. An agent's prompt lists the skills it may load, by name and description; `skill_load` returns a body. Nothing in the code decides when a skill applies.
- **A tool:** name, family, tier (read, write or external), description, parameters, and where it runs: in the runtime, or in the extension over the link (`tool.call`), which is how an extension's own tools and MCP tools run.
- **Three sources for each:** built in, an extension's, the user's. A user's definition with the id of a built-in or an extension's overrides it, and a reset restores the original. The user makes, copies, edits, switches off and deletes definitions on the page.
- **What an extension keeps as its own.** An extension's agent definition may name fields it keeps (`owns`: `instructions`, `tools`, `name`, `description`). Where the user has a version of that agent, those fields come from the extension's definition as it is at each run, and the user's version gives the rest (connection, model, effort, tool calls, limits). A save never stores them, and the page shows them as the extension's. Owned tools stand over Settings too: a tools value there for that agent is neither read nor stored, while its other settings still apply. An extension's skill marked `owned` is its alone: a copy the user keeps under its id is not used, and the page doesn't save one.
- **What a user's version lacks.** Where a user's agent stands over a built-in or an extension's agent that doesn't keep its tools, the page names the tools the original has now that the user's lacks, with one button that adds them. Nothing is added without it.
- **Whom a skill is for.** A skill may name the agents it is offered to (`agents`); without it, every agent that holds `skill_load`. The list an agent is told and `skill_load` both keep to it, and `skill_load` says whom a skill is for when another agent asks for it. A skill names the agents its procedure starts (`starts`): where the backend leaves one out, the skill isn't offered at all (the chronicler's two skills, without the chronicler and the story reader).
- **What each agent can use.** `backend.agents.held(userId, chatId)` gives, for each agent that can run in a chat, the tools it holds there and each tool it names that it can't use, with why: switched off by the user, withdrawn by the extension's claim, or not registered.
- **The registry** the runtime uses for a turn is the merge of the three, read at the turn's start.
- **The tools the user added.** An agent's tools may name `@added`: every tool that isn't built in (an extension's own tools, and those of the MCP servers switched on for agents), including ones added later. The main agent's default tools hold it, so an added tool is one the main agent can call with nothing else to set, and a sub-agent whose definition names such a tool is given it under the default grant (§14). The pages show it as a plain choice, never as `@added`. No built-in tool is part of it: a built-in that acts outside LumiAH (`web_search`) is given to an agent by name, by the user.

## 14. Delegation

- `delegate({agent, task, files?, as?, to_reply?})` starts a registered agent as a sub-agent with its own session. Its answer is the tool's result. Several calls in one round run at once, under a setting.
- **`as` says which one the sub-agent is**, where its definition stands for many (an extension's character, by its id). Its tools that run in the extension are told it with the rest of who called (§21), the trace says it where the agent starts (`AgentStarted.as`), and the extension's model hook is asked with it. It is offered only where an extension builds LumiAH in, and is refused past *Instance name length* (`delegation.asChars`, 200).
- **`to_reply` hands the reply's stream on** (§3.4): the sub-agent's answer streams into the reply as it is written, and is the call's result too. Only an agent that may release the reply itself is offered it. The text of each of the sub-agent's model calls is held until it is *Hold before a handed-on reply streams* long (`delegation.replyHoldChars`, 200 characters) or the call ends without a tool call, then it streams: the line or two a model writes before a tool call never reaches the user, and released text is never taken back. Its reasoning stays its own. While its answer streams, any other release is refused in words that say to wait for it. The sub-agent writes the reply as its answer, so it is given no `reply_write` of its own.
- **The handle lives until the turn ends:** `agent_message({handle, text})` continues that agent, under a revision cap.
- **A depth setting** decides who may delegate: 2 as shipped, so the agent a run starts with and the agents it starts. A job that an agent starts stands one deeper than that agent (one the user starts at 0), and its agent is given tools by the same rule as a sub-agent: so the main agent's job may hand tasks on, and whoever takes them may not. A job's sub-agents are counted against a setting of the jobs' own (no limit as shipped: its allowance bounds them), not against the turn's.
- **A sub-agent's writes** are its own versioned writes.
- **A sub-agent's tools** are its definition's, never more than the agent that started it may grant: by default no tool that agent doesn't hold itself, and a setting gives every sub-agent whatever its own definition names. A definition may say for itself (`grant`): one that keeps its own tools whoever starts it is given all its definition names, even by an agent that holds none of them. That is for an agent whose tools are its own trade, which the agent that hands it tasks is deliberately not given. A user's definition of the same id decides in its place.
- Every sub-agent's session appears in the live view under the agent that started it, and is kept with the turn's transcript.

## 15. Jobs

A job is an agent run that outlives the reply.

- **Tools.** `job_start({agent, task, when, as?, lane?, due?})` with `when` as `now` (it runs beside the turn) or `after_reply`; `job_list`, `job_read`, `job_cancel`. `as`, `lane` and `due` are offered where an extension builds LumiAH in.
- **Lanes.** Among the jobs waiting for a place (*Jobs at once*), every `soon` job goes before any `later` one (the default), first come first through within each.
- **Due by the next turn.** A job started with `due: "next_turn"` is waited for at the start of the next turn on the path (the one after the turn it belongs to), until it ends or *Wait for jobs due* has passed (`jobs.dueWaitMs`, a minute). The thinking block says so while it waits. A job that ended meanwhile is heard of as any ended job is; one still running is named in the main agent's opening.
- **Nothing starts a job except an agent's `job_start` call or the user on the page.** A test fails if any other code does.
- **Limits, all settings:** jobs at once, tokens per job, time per job, tokens per day; and the user's controls: off, pause, cancel.
- **A day's limit never fails a job.** A job that runs into the jobs' tokens per day, or into the user's caps on a day's spend (§20), stops as one whose allowance ran out does (§22): its session and what it wrote are kept, and its report names the limit and where to change it. It carries on from where it stopped once the last 24 hours count less or the user has raised the limit; carried on while the limit still stands, it stops there again without a call.
- **Basis.** A job belongs to the record of the turn that started it. Its report is a blob listed with that record. Its workspace writes are versioned writes, made when they happen.
- **Off the path.** When its basis is no longer on the chat's active path at the moment it would write or report, the job stops, and its report is marked off the path. Writes it already made to the chat area stay with the path they were made on.
- **Hearing about it.** At the start of its next turn the main agent is told which jobs finished or failed since, with each report's opening and how to read the whole. The page lists every job with its state, agent, spend and report, and tells the user when one finishes or needs them.
- **A runtime restart** leaves a running job marked interrupted, with what it had done kept. The user or an agent may start it again.
- **Run again** from the page starts the same job again: the same agent, `as`, task, lane and due, the same starter's tools, and the same turn it belongs to, so an extension knows it for that turn's job. It is told what its first run was told, and, in one line more, that it is run again and why its last run stopped. Once the reply it was started from is off the chat's path, it isn't run at all, and the user is told why. An agent's `job_start` with `again` starts the job again as its own, for its own turn.
- **An answer cut while thinking.** A job whose agent's answer ran out of room before it wrote anything (its model spent the room thinking) fails in words that say so, and where to give it more room.
- **A failure that lasts.** A job that failed on what it runs on is marked so (`lasting`): no connection to run on, a call its provider refused for its key, its model or its account, or an agent that is gone. Run again, it fails the same way until the user changes that. Whoever starts jobs (an extension carrying work on in new runs) can tell it from a failure that may pass.

## 16. MCP tools

A server the user has set up in Lumiverse appears in the tool registry once the user switches it on for agents, each tool as `mcp:<server>:<tool>` with the tier `external`. Calls go through Lumiverse on the extension's side. Switching a server on is all it takes: the main agent holds its tools from the next turn (§13), and they are called without asking unless Settings say external tools ask first (§17).

## 17. Approval

- **Settings decide for each tier,** with an override per tool: allow, or ask. Every tier's default is allow. A tool that acts outside LumiAH is one the user set up and switched on, or installed with an extension, and that was their consent; asking first is one switch away, for the tier or for one tool.
- **"Ask" holds the call** and shows a card in the live view with the tool, its arguments and the agent asking: approve once, approve for this chat, or refuse (with a reason the agent is given). A setting bounds the wait; when it runs out the call is refused and the agent is told why.
- **Approval fails closed.** What comes back from an ask is outside data: only an answer that is exactly an approval (once, or for this chat) runs the call. A refusal is one; anything else is nobody's word, the call isn't run, and the agent is told so. A host passes the user's decision on exactly as it was given.
- **"For this chat" is kept** with the chat, each tool with when the user said so. The user reads what is kept, for one chat or for all, and takes a tool out again; every run that begins after that asks about it again.

## 18. Talking to a working agent

- **Say something:** a note the main agent receives at its next round, marked as the user's.
- **Pause and resume:** holds every agent of the turn at its next round.
- **Stop** (already there) ends the turn.

## 19. Side sessions

A side session is a conversation with an agent that is not a reply in the chat: the page's own chat with the main agent, or with any agent the user picks, about a chat or about nothing in particular. It has the same tools, workspace, guidance and live view. It is kept in the store, not anchored to a message, and it never writes to the chat's messages.

## 20. Spend and upkeep

- **Spend.** Every model call that reached its connection is recorded with its agent, connection, model, tokens and cost: one that was stopped, failed or was made again too, with the runtime's estimate marked as one, since its provider reported nothing. The page shows spend by day, chat, agent and connection (each connection by the name the user's runtime gives it, else by its id), and the caps in force. A cap that is reached refuses the next call in plain words that name the setting; and a cap is asked about the call about to be made, with its prompt as estimated and what the calls under way hold, so neither one large call nor several agents at once pass it unseen. A cap stops agents' work, never the writer's call of the reply the user waits for, which is made and recorded.
- **Cost.** A provider's own cost is used where it reports one. Otherwise the user's prices give it: the price under the model name the provider reported, else under the model the call asked for, else the longest priced name one of those starts with (a provider often reports a dated name). With no price of the user's, the provider's published price gives it, where the runtime knows one (§26). Either way it is an estimate, marked as one (≈), never a bill. The call's usage in the trace names the price that gave the cost.
- **A cached re-read counts at what it costs.** A long run re-reads its own conversation at every call, and most providers bill a prompt token read again from their cache at about a tenth. So every limit on prompt tokens (per agent, per turn, per job, per day) counts such a token at a weight: a setting, a tenth by default, 1 to count it in full. A limit's message says what was counted against what is allowed, and the weight. The pages show the true counts; a cap shows both.
- **Upkeep.** Prompts, transcripts and the spans a compaction replaced are kept for a time that is a setting. A sweep removes blobs nothing refers to. The page shows what is stored and how big it is, and can run the sweep.
- **A chat that is deleted is forgotten.** When Lumiverse says a chat was deleted, the backend asks the user's runtime to forget it (`chats.forget`, §6): its `learned/` area and its own area's heads, its jobs and their reports, its side sessions, its approvals, how its lore last stood and its search vectors go, from the runtime's store and from its mirror alike (§27), and nothing of another chat's. The texts those named go with the next sweep. It is refused while a reply is being worked on in the chat, and asked again later.

## 21. An extension that uses LumiAH

Another extension builds LumiAH into itself (§1). What it may supply:

- **Tools,** which run in its own backend (§13). A call tells the tool who made it: the run and its kind (a turn that answers a generation, a job's run, a side session's turn), the calling agent and its definition, which instance of it the agent is (`as`, §14), whether that agent is the run's main agent, and the agents over it, from the main agent down to the one that started it, each with its `as`. So an extension tells the run's main agent from an agent it handed a task, whatever definitions the two run as.
- **A file kept for the agent that called.** An extension's tool may keep a file in LumiAH's workspace as the agent that called it (`workspace.writeAs`, with the run, the call and the agent as the call was handed them). It is the write `workspace_write` makes: versioned, under the same limits and the same guard, in that turn's change set, and named on the call's result in the live view. The chat's own area takes it only while the run is under way.
- **Agent definitions, skills and guidance levels,** as its defaults; the user's still override them.
- **A main agent** for the chats it claims, in place of LumiAH's. A claim may also say (`ChatClaim`): what of the request the main agent is shown (`request`: the whole as Lumiverse assembled it, the default, or only the user's newest message, which a sub-agent given the request is shown too); and that the reply is only what the agents release (`reply: "released"`, §3.4: no writer is called, `write_reply` isn't offered, and a turn that released nothing fails in plain words). Where the user's settings can't be read at all the claim can't be asked either, so that turn goes as any such turn does (§3.2).
- **Nothing stands in for what a claim needs.** Who leads a turn is settled before anything is read or sent. Where the claim names an agent that can't run in this run (there is no such agent, it is switched off, or the extension's definitions gave no answer in time or failed), the turn doesn't start: no model is called, and the turn fails with words that name the extension, the agent, why it can't run and what to do (switch it on on the Agents page; give the extension longer with *Wait for the extension*, named with where it is changed: the runtime hands the core that place as the user's Settings show it, `HarnessOptions.place`, a mounting extension's `settingsAt` included). LumiAH's own main agent never takes a claimed chat's lead. Nor does a run about a chat start where the extension gave no answer on whether it claims it (its wait ran out, or the call failed): a reply, a job's run and a conversation's turn fail in the same words, since run as one of LumiAH's own chats it could be answered wrongly. Definitions that gave no answer cost only what needs them: a run that goes on without them says in its live view that the extension's agents and skills are missing, and why; a job or a conversation whose agent is the extension's fails with that, and can be started again.
- **Who leads, on the Agents page.** The page asks the claim of the chat open in Lumiverse (`lah.chat.lead.get`) and says who leads its replies: the agent the claim names is marked as leading them, and LumiAH's Main agent (and the Writer, where the reply is only what is released) as taking no part in them; they still answer a conversation or a job started with them. With no chat open it says how it goes in general.
- **The anchor** (§5), when it keeps its own record per message.
- **The writer's request:** it may rewrite the messages the writer is sent, to place what it prepared where the user's preset expects it.
- **Hooks on the turn:** when a turn begins, when the reply has been written, and when the turn ends.
- **An agent's model:** `agentModel`, asked as each agent of a run starts with its definition, its `as`, how it stands (an agent the run starts itself, a sub-agent, a job's agent) and who started it. Its answer names the connection (one of the runtime's, by its id, §26), model and effort it runs on; null, or a member left out, leaves the definition's own. A connection named without a model runs that connection's own model; one the runtime doesn't have leaves the agent on the runtime's default, as an agent's own connection that is gone does.
- **Its word on the reply:** `releasing` is asked before each passage an agent releases with `reply_write` goes out. A refusal is the call's answer and nothing streams; null lets it go. It fails closed: a failure, no answer within *Wait for the extension*, or an answer that is neither lets nothing go, and the agent is told it may try again. Each passage is asked about and goes out in the order the calls came. `released` is told of each passage that went out, and of a handed-on answer once it ends (§14), which is never asked about. Without `releasing` every passage goes.
- **Pages:** LumiAH's pages are components it mounts in its own drawer.
- **The runtime:** it ships the runtime beside its backend, the same `dist/lumiah.js` LumiAH ships, built from LumiAH's source, which links to it by its identifier (§6) and updates itself from it (§29). `docs/EXTENDING.md` says what its build does.

LumiAH's own tests include a sample extension that supplies one of each, so this surface is exercised without any real extension.

## 22. A long objective

Some work is too long for a turn and ends in no reply: learning the story of a chat that already has thousands of messages, or putting a workspace in order. It is a job the user starts on the page.

- **What the user gives:** the objective in their own words, the agent to do it (the main agent unless they pick another), and an allowance of tokens and time for this job alone.
- **A plan first.** An agent that can write files is told its allowance and asked to say, before it works, what it will do with it: where it will read closely, where a summary is enough, and what it will leave out. The plan is a file in `learned/`, which it keeps true as it goes. A smaller allowance should give a narrower plan. An agent with no tool that writes files is told its allowance and its objective, and nothing about a plan or files: it is told only what it can do. Whoever starts a job may keep its plan file with tools of their own (`plan` with `planWords`, as an extension's prepared start does, whose plan is of more than one run): the agent is then never asked to write the plan, nor told that its allowance shapes it. It is told the starter's words of the plan in that place, as it begins and as it is carried on, in texts the user can replace as they can the ask for a plan.
- **Steering.** The user can say something to the job while it runs, and pause and resume it (§18 applies to a job as it does to a turn). A paused job stays paused across a runtime restart.
- **When the allowance runs out** the job stops with a report of what it did and what is left. The user can grant more, and it carries on from its own session. A day's limit stops it the same way, and it is carried on with nothing more granted (§15).
- **What it leaves:** files in `learned/`, among them a plain list of what it has not verified.
- **It may delegate, and start jobs of its own,** all counted against its allowance.
- **No basis record.** A job the user starts belongs to the chat, not to a turn. It writes `learned/` and `~/`, which no swipe changes. A write to the chat's own area is refused in words that say why, unless the job was started to write it (`area: "chat"`, as an extension's prepared start is): it then writes the chat's own area at the latest reply on the path, as the page does, and beneath that reply as well (the area its turn started from), so a swipe or a regenerate of the newest reply starts with the job's work, as does every turn after it on that path. When the job ends, the records it wrote beside are written again with their areas as they stand, so a branch cut there has the job's work too; a branch cut before any record reads the area of the chat it was branched from until it writes its own. A swipe of the newest reply made before the job ran keeps the files it had. Such a job may name its plan file (`plan`, anywhere in the workspace) in place of `learned/plans/<id>.md`, and is told in words of its own that it may write `/`. Started again, a job keeps its `as`, `area` and `plan`.

## 23. A story's book

LumiBooks is another extension: it summarizes a chat's older messages into chapters and arcs, kept as entries of a world book it makes for that chat. Where a chat has one, the agents can read it as a book.

- `book_outline` gives the tree (volumes, arcs and chapters, each with the messages it spans) and the coverage: which of the chat's messages no chapter covers, and which have changed since they were summarized.
- `book_read` gives an entry's text.
- **Both are worked out by code** from the world book and the chat. Neither makes a model call.
- The tools are offered only in a chat that has a book.

## 24. Lore and history

Two things decide whether a long story holds together: the lore a reply must be faithful to, and what the chat itself established, at whatever level of detail the moment needs. The prompt Lumiverse assembles holds a part of each. The agents' work is to know which part, and to reach the rest fast. Lumiverse is the data surface: LumiAH adds no store of its own where Lumiverse already keeps one. The runtime's copy of chat and lore (§28) holds Lumiverse's own rows, in memory, and answers only for what it can vouch for.

### 24.1 What the prompt already holds
Each turn the main agent is told, in the request itself and with no tool call:
- **Lore in the prompt:** each activated entry by id, title and size, and how it got there (a key that matched, or a vector match with its score). Lumiverse flags each world-info message of the prompt, so this is exact.
- **Lore not in the prompt:** an index of the other entries of the chat's books: id, title, keys, size. It is ordered by how well each matches the recent messages and cut at a size setting, with a count of the rest. Entries the user switched off are left out unless a setting includes them.
- **History in the prompt:** which of the chat's messages the prompt holds word for word, by number; which it doesn't; and what stands in for those (a book, §23; Lumiverse's own summary or memories blocks), each named.

Each of the three is a text the user can replace, has a size setting, and can be switched off.

### 24.2 Lore tools
- `lore_index`: every entry of the chat's books: id, title, keys, size, book, and its state (in the prompt, always on, switched off). Filters by state, book, or text in a title or key.
- `lore_search`: several queries in one call. Ranked over titles, keys and text, with titles and keys weighted (settings). Each hit comes with its best lines, its state and why it matched. Where the user has an embedding connection, matches by meaning are merged in (§24.5).
- `lore_read`: several entries whole in one call, paged.
- `lore_grep`: an exact string or a pattern.
- `lore_related`: one hop of the lore's own links: the entries that mention this entry's title or keys, and the entries it mentions.
- `lore_about`: everything the books hold on a name: the entries titled or keyed with it, then the entries that mention it.

### 24.3 The lore the writer sees
The main agent decides what lore reaches the writer, entry by entry, without retyping any of it: `write_reply` takes, beside the brief, entries to add and entries to drop.
- **An added entry's own text** goes into the writer's request where Lumiverse puts world info, beside the entries already there; where the prompt has no such place, before the brief.
- **A dropped entry's text** is taken out of the writer's request.
- Settings say whether the main agent may add and whether it may drop, and cap what it adds. The live view shows each entry added and dropped, and the exact prompt shows the result.

### 24.4 History tools
The level of detail a moment needs slides: a line of summary is enough for most of the past, and the exact words are needed for a little of it. The tools go from coarse to exact.
- `chat_outline`: the story as a table of contents with the messages each part spans. It comes from the book where the chat has one (§23); else from the arcs Lumiverse's own memory has made, where the user has that on; else from a plain skeleton worked out by code (breaks at long gaps in time, each stretch by its opening lines, who speaks and how long it is).
- `chat_about`: the trail of a name or a phrase through the chat: where it first appears, where it last appears, how often, and its most telling lines in order. "What did the chat last establish about the brass key" is one call.
- `chat_search`: several queries in one call, ranked, with hits grouped by stretch so one exchange doesn't fill the page, each with its lines of context, message number and date; filters by range and by who spoke. Matches by meaning are merged in (§24.5).
- `chat_grep`: an exact string or a pattern.
- `chat_read` and `chat_around`: the messages themselves, by range, or around one message.
- `memory_search`, `memory_entity`, `memory_arcs`: Lumiverse's Memory Cortex, where the user has it on: retrieval over the chat's memory, what it has recorded of a person or thing (facts, relations), and its arcs.
- `databank_list`, `databank_search`, `databank_read`: the user's databanks that apply to the chat.
- `web_search`: the user's own web search provider, where they have set one up. Its tier is external (§17).

A tool that rests on something the user hasn't set up is not offered.

**What counts as the story.** Not every message of a chat is story. The user may hide a message from the prompt in Lumiverse. With Lumiverse's Sovereign Hand, the user's own messages are directions to the model, not events in the story. Three choices say what the agents read as the story:
- **Hidden messages:** left out (the default), or read like any other.
- **Whose messages:** everyone's, only the model's replies, or as Lumiverse's Sovereign Hand says (the default): only the replies while it is on. Lumiverse doesn't tell extensions yet whether it is on (no part of Spindle reads the user's settings, and `{{loomSovHandActive}}` resolved by an extension always says no), so the adapter's `chats.sovereignHand` answers null, and following Lumiverse counts everyone's messages. The pages say so.
- **The newest message,** where only the replies are the story: given to the main agent as the direction for this reply (the default), or left out too.

The user sets them in Settings. A chat may choose otherwise, member by member, kept beside its switch. An extension that answers the chat may set any of them in its claim (`ChatClaim.story`), and is asked with what holds below its word (`ClaimAsk.story`, `ClaimAsk.sovereignHand`). The strongest word holds: the claim's, then the chat's own, then the user's. Each run resolves it once, and its hooks are told what holds (`RunBegan.story`).

What the story leaves out, the agents never see:
- The history tools neither list, search, match nor return a message left out. Each says in one short line how many it left out and why. The other messages keep their numbers.
- The chronicle's readers and Learn this story read only the story; a message left out is nothing to learn, and counts in no figure on the page. A citation still checks against the whole chat, but a chronicle line whose cited messages are all left out is not given to the main agent.
- Search by meaning never embeds a message left out.
- The request Lumiverse assembled is shown to the main agent as it is: it is the preset's.

The chronicle is kept and learned by LumiAH's own chronicler and story reader (§24.7). In a chat where an extension puts an agent of its own under either name, or where the user switched one off, LumiAH offers no upkeep and refuses Learn this story, saying why.

### 24.5 Search by meaning
Where the user has an embedding connection and the setting allows, LumiAH keeps a vector for each lore entry and each chat message, in the core's store (§27) by the text's hash, so an unchanged text is never embedded twice. New text is embedded in the background under a daily cap. `lore_search` and `chat_search` merge matches by meaning with matches by word. Without an embedding connection, search is by word and says so. The page shows how much is embedded and what it cost.

### 24.6 Speed
- Indexes are kept between turns and rebuilt only for what changed.
- One call carries several queries or several ids.
- §24.1 means the common turn needs no lookup call to know what exists.

### 24.7 The chronicle
What the story has established, kept so that no agent has to read the chat again to know it.
- **Files** under `learned/chronicle/`: the outline (parts of the story with the messages each spans), what is established (facts), open threads (promises, questions), and the cast (who is where, and in what state).
- **Every line cites the messages it rests on.** The chat tools print each message with a short citation (its number and a few characters of a hash of its text), which an agent copies.
- **`chronicle_check`** is worked out by code: it lists the lines whose messages are gone or have changed, as after a swipe or an edit. Lines that fail it are left out of what the main agent is given.
- **The chronicler** is a built-in agent. The main agent starts it as a job after a reply, as a built-in skill describes; the user can switch that off, or run it by hand.
- **The top of the chronicle is pinned** into the main agent's context under a size setting. From there it goes down the scale: outline, trail, search, the messages themselves.
- Learning an existing story (§22) builds the same files, from the book and the chat.

## 25. The runtime

Every chat LumiAH answers runs in the runtime: a process of its own beside Lumiverse, which the user starts once (`docs/RUNTIME.md`). The agents, their tools, sessions, workspace, jobs and side sessions run there; the extension serves the link, the pages and what is Lumiverse's.

- **One switch.** A chat is on or off. Switching it on pins it to the user's loopback connection, which must exist (the runtime makes it, §6; with none, switching on is refused in words that say how to make one); switching it off gives back the connection the chat had. A chat's jobs and side sessions run where its turns run.
- **No fallback.** While the runtime is down (stopped, not linked, refused for its link version), the replies of the chats switched on fail, and nothing answers them in its place. LumiAH tells the user: a toast as a reply is about to go to a runtime that isn't linked, and the chat's view and Home say the runtime isn't answering, with the way to the Runtime page.
- **No connection, no reply.** The runtime calls models on its own connections (§26). With none, a reply is refused before any work, in words that say where to add one; Home and Live say so too, with a button to the Runtime page's Connections.
- **Disable and uninstall.** Lumiverse gives an extension no moment at either, so nothing is undone then: a chat switched on stays pinned to the loopback connection, and its replies fail until the user switches it off first, or gives the chat another connection afterwards (`docs/RUNTIME.md`).
- **Two extensions.** With LumiAH and an extension that has it built in both installed, each answers only the chats switched on in it (§7), each in a runtime of its own.
- **Built-in mode,** where the main agent worked inside Lumiverse while it waited to send the prompt and Lumiverse's own generation wrote the reply, is gone from this branch; LumiAH's `main` branch still has it for now. A chat switched on that way reads as off here until it is switched on again, and the settings only it read (`reply.warnMs`, `reply.pendingMs`, `transport.builtin`) are passed over quietly.

## 26. The runtime's connections

Every model call an agent makes, and every request passed through the loopback (§2), goes from the runtime straight to its provider through pi-ai (`@earendil-works/pi-ai`, pinned, bundled into the runtime alone), on the runtime's own connections (`src/runtime/models/`). Lumiverse's connection profiles are not used for agents: the loopback connection is only Lumiverse's way in to the runtime.

- **A connection** is a provider, how its calls are signed, an address, a model, an effort and headers (`{ id, name, provider, auth, baseUrl?, api?, model?, effort?, headers? }`). The providers offered: Anthropic, OpenAI, Google Gemini, OpenRouter, DeepSeek, xAI, Groq and Mistral, and for any server that speaks one of two APIs (a proxy, a server on the user's own machine, a provider not listed), *OpenAI-compatible* (Chat Completions or Responses) and *Anthropic-compatible*, each with the address it must be given. Bedrock, Vertex AI, Azure and GitHub Copilot are not offered; any other provider is reached as OpenAI-compatible at its address.
- **How its calls are signed:** with its own key (`key`); with the runtime's sign-in to the provider (`signin`: Anthropic with a Claude account, OpenAI with a ChatGPT account); or with nothing (`none`: a compatible server that asks for no key). One sign-in per provider per runtime.
- **The default.** One connection is the default (the first one made, until the user picks another). An agent that names no connection runs on it, and so does one whose connection is gone (removed, or one of Lumiverse's from before the runtime kept its own): its calls name the default, and its page says so. With no default, an agent stops before its first call, in words that point at the Runtime page's Connections; with no connection at all, a reply is refused before any work (`no_connection`). Settings that name a connection (an agent's, *One tool call per answer*, the throttles) name the runtime's connections by id.
- **Secrets stay in the runtime.** Keys and sign-in tokens are kept in the runtime's own folder (`secrets.json`), and header values with their connections (`connections.json`), both their owner's alone; each goes out only with the calls of the connection it was given for. A page sees whether a key is set and its last four characters (for a key of 12 characters or more), and of a header its name and whether it has a value. A key crosses once, in its save: from the page through the extension's backend to the runtime, over the link or through Lumiverse's proxy, as any key typed into Lumiverse passes through Lumiverse; nothing on the way keeps, logs or traces it. Nothing of a secret goes to a log, a trace or the extension's storage, and every word that leaves the model layer is cleaned of them and then cut to 2,000 characters, so no cut leaves part of one behind. A connection whose provider, or whose address's origin, changes keeps its key and its headers' values only where the same save gives them again, and a new connection starts with only the key it is given. An address holds no name, password, query or fragment, and a sign-in connection takes none: it calls its provider's own. The model layer follows no redirect, so a key and its headers stay with the address they were given for; Gemini's calls are the one exception, since pi-ai gives Google's client no fetch of the runtime's. What the providers' SDKs would read for themselves in the runtime's environment (extra headers, keys, addresses, an organization or project id, Vertex AI in place of Gemini) is taken out of it before any call, and the log names what was taken, so nothing ambient signs or steers a call. The machine's own proxy and certificate settings, which every program on it reads, still apply.
- **Per agent.** Each agent's connection, model and effort are its own (Settings, its definition, an extension's `agentModel`, §21). Efforts: `off`; `minimal` to `max` as the provider's own level nearest to each; `auto` and `inherit` as the connection's own effort, else the provider's default. Each sampling parameter reaches a provider only where its API takes it; the others are left out, never sent to fail a call.
- **Reasoning across a tool loop.** A model's thinking and its signatures ride in the core's carriers, so the next call of a tool loop hands them back to that model exactly.
- **The prompt cache.** Each agent's calls name its session, and the provider keeps their cache as long as *Kept for* says (`cache.retention`: none, a few minutes as shipped, about an hour where the provider offers that). The provider places its own breakpoints and the core marks none; a value kept at the retired `cache.breakpoints` is passed over. An agent's session is let go when its run closes. That is housekeeping after the run's work: a letting-go that throws is logged as such (`linkHost` in `src/runtime/host.ts`), and the run stands as it ended, its record, the other agents' sessions and its spend untouched.
- **Usage and cost.** A call's usage comes back as the core reads it (§20): a provider's own bill as `cost`; else, where the catalogue knows the model's published price, that price's sum as `list_cost`, an estimate.
- **A silent answer.** A call whose answer has begun and then gets nothing at all from its server for *Silent answer ends after* (`runtime.answerSilentMs`, 5 minutes) is ended and made again, as a dropped stream is. Before its answer begins nothing is cut short (a model may be reading a long prompt, or thinking unseen); after, any byte from the server counts, and for Gemini only pi-ai's own events do. A connection's Test and a server's list of its models wait *Provider wait* (`runtime.providerMs`, a minute), and a list is read no further than 8 MB.
- **Sign-in.** The page shows the provider's address, with a note to read first; the user signs in there and pastes back what the provider gives (Anthropic: a code; OpenAI: the whole address the browser was sent to, `http://127.0.0.1:1455/…`, which finishes the sign-in by itself where the browser runs on the runtime's own machine and port 1455 is free there). A flow stays open ten minutes. One that ends without a sign-in (cancelled, left open too long, replaced, signed out, refused, the port taken) says why on the page for ten minutes. Tokens are renewed by themselves as calls need them; a renewal that fails asks the user to sign in again, without saying why it failed. On an Anthropic sign-in the runtime sends requests the way Claude Code sends them (Claude Code's own line first in the system prompt, and the names of tools that share a name with one of Claude Code's written its way), and the note says so before the user goes. Known limits, pi-ai's own: Anthropic's sign-in address carries the proof its code is redeemed with, so whoever sees both that address and the pasted code could finish the sign-in first; and a program on the runtime's machine can end an OpenAI flow that is open by calling its address on port 1455, in words of its own that the page shows as the provider's.
- **Copy from Lumiverse.** The page lists the user's Lumiverse connections (never a loopback, never with a key) and makes a runtime connection of each under the same id, with its name, provider, address and model, so a setting that named it still does. Keys are typed again.
- **Page ops,** asked of one runtime by its relay (§6): `connections.list|save|remove|default|test|models` and `signin.start|finish|cancel|out|state`. With several runtimes linked, each has its own connections, and an agent runs on those of the runtime its chat runs in. A page about a chat asks the runtime that plays it (the chat's view names it, `ChatView.runtime`), else the runtime heard from last. An agent's start in the trace names the connection its calls went on (`AgentStarted.connectionId`), put there once that connection was read for its first call, with its name then (`connectionName`) and, where the agent's settings name a connection the runtime doesn't have, that id (`gone`). A transcript names each agent's connection so (one kept before names were, as the chat's runtime lists it), its totals and its CSV name each call's, and its feed says once of a `gone` id which agents named it and that they ran on the default. Spend names a connection as the user's runtime heard from last lists it; each gives the id where the connection isn't listed.
- **What the road through Lumiverse did that this one doesn't** is listed in `docs/RUNTIME.md`, *What the runtime's model calls can't do*.

## 27. The working store and its mirror

The core's documents and blobs (the workspace, sessions, transcripts, jobs, side sessions, spend, search vectors) are kept on the runtime's own disk as the working copy, with the extension's storage behind them as their durable mirror (`src/runtime/store/`). One runtime at a time keeps such a copy for a user and an extension; the extension's backend says which (`src/extension/backend/mirror.ts`).

- **Where.** `<the runtime's folder>/store/<a hash of Lumiverse's address, the user and the extension>/`: `docs/` and `blobs/` as the extension's storage lays them out (so nothing is migrated), `journal/` (a file for each path the mirror doesn't hold as it stands here), `tmp/`, and `identity.json` (whose data it is, the copy's own id, and how many of its changes the mirror took). Folders and files are their owner's alone.
- **Reads** are answered from the working copy, else from the mirror, whose answer is kept from then on. A blob is checked against its hash both ways; a damaged copy is read from the mirror again.
- **Writes** land on the disk first (a temporary file renamed into place, the path noted in the journal before it), and the core goes on. A sender brings the mirror up to date behind it, one path at a time in the order they were last written, the last write of a path winning, and waits longer between tries (from a second, doubling up to a minute) while the mirror can't be reached. A restart sends what the journal still names.
- **Barriers.** `settle()` waits until the mirror holds everything written before it. The runtime settles before a turn's record goes on the reply's message, before any other record is written on a message (a rollback, a job's end), and when it stops while the link is up; it waits *Storage wait* (`runtime.storeWaitMs`, a minute), then goes on without: nothing is lost, it stays on the runtime's disk and follows. The backend's own readers of that storage (Sessions, a transcript, a call's prompt) ask the runtime to settle first (`store.settle`) for *Wait for the runtime's saves* (`pages.settleMs`, 5 seconds); past it they show what the storage holds, and say so (`SessionView.behind`). With no runtime linked they read the storage as it is.
- **Lists.** A list of documents (`store.list`) is the mirror's, with the changes not yet sent laid over it. The sweep's list of blobs is the mirror's once it holds everything, and upkeep removes a blob from both.
- **Refused for good.** A change the extension's storage refuses by a rule it holds to (a path it doesn't take, a frame larger than *Largest frame joined*) leaves the journal and the working copy at once, is logged, and is listed on the Runtime page; a settle that waited for it is told in the storage's words. The link's `too_large` means only that.
- **Refused itself.** Where the extension refuses the runtime itself (it doesn't know it any more: forgotten on the Runtime page, or registered anew by `lumiah up`; or the runtime's link is refused), no wait mends that while the process runs (`WorkingStoreDeps.disowned`). The sender stops, and what waits on the mirror (the copy's opening, every `settle()`, the stop's among them) is told at once rather than at the end of *Storage wait*, while the link still looks up until its next ping hears the refusal. What wasn't sent stays in the journal, and goes from the next runtime started on that folder that the extension knows.
- **Room.** Past 2 GiB of blobs, those the mirror holds are let go from the disk, least recently used first; one not yet mirrored never is. Documents have no cap.
- **Who holds the mirror.** The backend decides at each hello, and says it on the hello's answer and in a `mirror` push whenever it changes: the mirror goes to the first runtime that asks for it; back to the same working copy at once whenever that one says hello again (a new socket, or the runtime started again on its folder); and to another only once the one that holds it has been silent longer than *Quiet after* (`link.quietMs`, 2 minutes). It moves at no other time, and no runtime takes it by itself. A runtime that stops cleanly settles and then lets it go (`mirror.release`), so the next one holds it at once. Who holds it is kept in the user's storage (`mirror-holder.json`, beside the registry) before a grant is answered, so a worker started anew gives it back to the runtime that held it. Until the backend has said, the store's operations wait; a backend that says nothing of it (one built before working copies) leaves the runtime without a copy.
- **A runtime without it** keeps no working copy: it reads and writes the extension's storage straight, as every runtime did before working copies, which is slower and just as correct. The one that holds the mirror is told at once of each document another runtime wrote or removed and each blob it removed (a `mirror` push), and drops what its copy holds of it, so its next read is the storage's. Where it can't be told (its link is down), the user's count of what a holder may have missed goes up, and at its next hello it drops everything its copy took from the storage; what it hasn't sent yet stays.
- **Losing it.** A write from a working copy names the process that holds the mirror (`mirror`); one from any other process is refused for good (`conflict`). A runtime refused so, or told another holds the mirror now, stops using its copy at once: what it hadn't sent is dropped, each path named in its log, every `settle()` that covered any of it is told, and its copy is wiped and begun again under a new id. It works straight on the storage from then on, and never asks for the mirror again in the same process.
- **The mark.** The mirror carries a mark (`mirror.json`, hidden from the core, which no runtime's own write may touch): the working copy it mirrors and how many changes it took from it. A copy is used, when its runtime is given the mirror, only when it is the mark's and not behind the mark's count. A folder copied to another machine or restored from a backup has taken fewer, and is thrown away for the mirror's, as is any other copy; its log and the Runtime page say so, with how many changes not yet sent went with it. The count is written beside the copy before the mark that names it, and the mark is brought up to date at most every 10 seconds while changes flow and exactly at a clean stop: a backup made less than 10 seconds before a crash is still trusted.
- **Forgetting a chat** (§20) removes its documents from both, then settles. Without a working copy it removes them from the storage straight, and clears any old copy of the chat left on the disk.
- **The Runtime page** shows each linked runtime's store (`store.state`): whether it keeps the working copy, or works without one and why (another runtime holds it, by name; or since when it lost it, to whom, and how many changes went with it); the changes waiting and since when, the last failure, what was last sent, its size on disk, the last time it threw its copy away for the mirror's, and the changes refused for good.
- **Two runtimes of one user and extension** share a few lists besides (all jobs, side sessions, spend), and changes two runtimes make to one of them at the same moment can overwrite each other.
- **Mounted in another extension,** the record of who holds the mirror is kept in that extension's storage: one holder per user and per extension, and the runtime knows nothing of it.

## 28. The copy of chat and lore

The runtime keeps a copy of the chats and world books its runs read, in its memory, so the core's reads of chat and lore are answered there rather than each crossing the link (`src/runtime/reads.ts`, `src/runtime/copy/`, `src/runtime/db/`).

- **What it answers.** The core's `chat.path` and `chat.messages`, `lore.books` and `lore.entries`, and the recall tools' reads of a chat's books and messages. The very logic the backend runs for them (`src/host/`, §1) runs over the copy, and the copy gives the very rows Lumiverse's Spindle API gives, so an answer is the one the link would give. The rest goes over the link: writing a record on a message, a chat's facts only the extension knows (`chat.info`), every chat's records for upkeep, what Lumiverse activated for a generation, a chat's book (§23), and what the copy doesn't keep (the list of chats, a character's name). Which world books every chat, the persona and the chat's character have comes with `turn.lore` at a run's start (§6); another persona's or character's are asked over `host.read` as they are needed.
- **What crosses.** For one reply, the chat and lore reads cross the link 6 times with the copy and 7 without, for a chat of 20 messages as for one of 2,000 (`test/runtime/chat-data.test.ts`). With the copy they are three `chat.info`, `book.read`, `turn.lore` and `recall.lore.activated`, and none carries a message, a book or a list of books; without it, the same but `turn.lore`, with the chat's whole path (`chat.path`) and its books (`recall.lore.read`).
- **Sources.** Lumiverse's database file, read directly where the instance's operator switched the reader on (below); else Lumiverse's HTTP routes, as the runtime's signed-in user. Over HTTP a chat comes in pages of 1,000 with only the shown swipe's text, and a world book with its entries; each page after the first starts on the row the one before ended on and must give it again at the same place, so a chat or a book that changed while it was read is read again from the start (three times at most). A chat or a book is read whole the first time a run needs it, and each request waits *Chat data wait* (`runtime.copyReadMs`, 15 seconds) at most.
- **Kept current** by Lumiverse's events, which the extension hands on to the user's own runtimes as it hears them (a message sent, edited, deleted or swiped; a swipe edited; a chat changed, deleted or branched; a world book or an entry changed or deleted; the library of books changed), numbered with the copy's other pushes: a number missing, or a ping that counts more than came, means one was lost, and everything held is read again. So it is when the link went down or reopened. A chat is read again on a message put in before others, a book on a change to it as a whole, and either on an event the copy can't apply.
- **The check before use.** A chat is checked against its source before it is used, unless it was checked or read in the last second; a run's first use of a chat checks it whatever the time, so a message sent just before the run is in it even while its event is on its way. Over HTTP the check sees the number of messages, the newest one and the chat's own row; from the database file, the file's own count of changes and a fingerprint of the whole chat. Where the check disagrees, the chat is read again.
- **What it can't see over HTTP.** A change Lumiverse makes with no event to a message before the newest (a persona's messages renamed in bulk, an extension's entry or the hidden mark written in place) isn't seen until the chat is read again, and *Chat data* says so of each chat. Lumiverse changes some of a book's entries with no event too, so over HTTP a book in use is read whole again once a second has passed since its last read. While the link is down, a chat is read whole whenever its check is due. The database reader sees all of these.
- **Never from a state it can't vouch for.** What the copy can't vouch for goes to the extension's own host over the link (`host.read`, for the runtime's own user), and that answer isn't kept: a chat not read yet while its source is down; a read or a check that failed, or got no answer within *Chat data wait*; an answer from one of Lumiverse's routes that isn't the one expected (a `404`, another status, a body of another shape), since those routes are no interface Lumiverse promises to keep: such an answer says nothing of the chat or the book, and over HTTP only the extension says one isn't there; a read the extension itself may not make (the copy reads with the user's own session, which no permission gates, so it keeps to what the extension was granted: `chats`, `chat_mutation`, `world_books`); a chat or a book larger than all the copy may keep (*Chat data kept*, `runtime.copyChars`, 32 million characters across chats and books, the least recently used let go first); a record the runtime wrote on a message, until the copy's row holds it (Lumiverse's event of the write may come before the link's answer or after it: either way the copy vouches for the record once the link has answered and its row holds the write); and every read while the runtime's sign-in to Lumiverse has ended, which the copy never takes for "no such chat" (*Chat data* then asks for the sign-in to be renewed). A route that answers so for three different chats or books in a row is asked nothing for a minute, its reads going to the extension at once. A backend that offers no copy (one built before it) has every read go over the link.
- **One user.** A runtime's copy holds its own user's chats and books, and nothing of another's: the session it reads with decides whose rows Lumiverse gives, a chat it was given that isn't its user's is answered by the extension, and an event that names another user is passed over.
- **A mounting extension's records,** where it keeps them outside the message (LumiRPEngine's ledger, `ownElsewhere`), are read over the link (`own.read`), and an `own` push says when a chat's records changed. The extension says so with `ownElsewhere.onChanged`, wherever its records change, its own pages' edits included; that has both the backend's own reader and the runtime's copy read the chat's records again. Where its records sit in one of LumiAH's own forms, its codec says where (`AnchorCodec.reads`); in a form only its backend can read, a chat's path is read over the link every time. One that declines lore (`declinesLore`) gets none from the copy either, and isn't asked `turn.lore`.
- **The direct database reader,** a source for a runtime on Lumiverse's own machine: read-only, through Bun's own SQLite, on Lumiverse's database file. It reads four tables (chats, messages, world books and their entries), with short statements scoped to the runtime's user, every value bound, and holds nothing between them. Before its first read, and whenever the file's schema changes, it checks the tables and columns it reads; a difference, a file that is gone, one it may not read, or one that isn't a database turns it off for good, with words that say why, and the copy reads over HTTP from the next read on. It never writes, checkpoints, attaches or creates a file. Known limit: a rewrite that keeps a text's length in bytes, made with no event and no new revision, is not seen.
- **Its switch** is the instance's operator's alone (`spindle.users.getRole`), kept in the operator's own storage (`database.json`) and off until switched on. The backend checks the role at every use (each hello's offer, each page request, each ping of a runtime that was given the file), gives the file's path to the operator's own runtimes only, and shows it on the operator's page only. The path is derived from where Lumiverse installed the extension (`spindle.manifest.entry_backend` lies under `<data folder>/extensions/<identifier>/repo/`, and the file is `<data folder>/lumiverse.db`), and nothing a page sends can set it. Switched off, or with its user no longer the operator, the runtime is told at once (`copy`) and reads over HTTP from then on. What an operator should know is in `docs/RUNTIME.md`, *The database reader*.
- **The Runtime page** shows each linked runtime's copy (`copy.state`, *Chat data*): where the agents' reads are answered and why, the source and why, the sign-in when it needs renewing, the reader's own state, the characters kept beside all that may be kept and the runtime's memory limit, each chat and book held (read when and why, what its last check saw and couldn't see, whether it is to be read again), what is too large to keep, the latest reads whole, every read sent to the extension and why (those Lumiverse's own routes didn't answer as expected counted apart, with the route and what it answered), and Lumiverse's events heard with each one found lost; and, to the operator alone, the reader's switch.

## 29. Updating the runtime, and how it is run

The runtime updates itself from the extension it links to, and keeps how it is run in its config (`src/runtime/update/`).

- **The offer.** The build writes the runtime bundle's sha256 and size into the extension's backend (`BackendEnv.runtime`). When a runtime says hello on another build (one refused for its link version too), the extension pushes `update { build, path, sha256 }`: the runtime file beside its backend, and that hash.
- **What the runtime takes.** Only from the file it was set up from (`source`, which `up` records: the extension's own copy it was run from), and only when the bytes there hash to the offer's sha256; those very bytes are written. A runtime set up from elsewhere (another machine, another folder) refuses, says why on the Runtime page, and keeps the update line. A config from before `source` was kept names none: that runtime takes its first update to this build by the update line, once.
- **How.** The one file written is lumiah's installed copy (the one its unit runs; else `<data folder>/lumiah.js`, or `<data folder>/<identifier>/lumiah.js` for another extension's runtime). The new build is written beside it, flushed, and must start there (`<bun> <file> --version`, on the Bun that will run it, within 30 seconds) before it is renamed over the old one. A build that can't start never takes the place of one that runs: the offer is dropped, and the page says why. A runtime that runs straight from the extension's file copies nothing: its restart is the update.
- **The restart.** Under its systemd unit, through systemd (`systemctl --user restart --no-block <unit>`). The unit's stop ends every process of the unit, `systemctl` among them while it is still there: one ended so (`SIGTERM`) had queued the restart, which is on its way, and is no failure. Otherwise the runtime stops serving as a stop does, then hands its process to its successor: the same Bun, the same file, `serve --config` with the same config. On Linux and macOS that is the same process (`execve`), so a terminal, launchd or a container sees nothing change. On Windows the successor is started on its own and the old process leaves; a task or service wrapper that started the old one doesn't watch the new one, and the page says so (`handedOver`). A copy that finds its port answered by another runtime waits (`waiting.json` in the runtime's folder, renewed every 5 seconds) and serves once that one stops; the serving one shows the waiting copy's process on the page.
- **When.** By itself while *Updates by itself* is on (as shipped) and nothing is under way: no reply, no request from Lumiverse, no job, no side session's turn. From the page's *Update now* at once, whatever is under way: the page says first what it ends, and afterwards what it ended. A failed copy isn't tried again by itself; the next hello offers again.
- **How it is run** (`runtime.service.get|set`, `runtime.update.apply`, asked of one runtime by its relay): its build; the update that waits and since when; what is under way; the memory limit and what holds it; *Updates by itself*; whether a new limit waits for a restart; the unit; the source; the file it runs from; a problem, with the line that mends it. The memory limit is a size systemd reads (`768M`, `2G`) or `infinity`, at least 256M, 1G until one is given. Under its unit, a new limit rewrites the unit (`MemoryMax`), has systemd read it again, and restarts the runtime when asked; elsewhere nothing holds the runtime to it, and the page says what would. `up` keeps the limit a runtime had unless given another: its config's, or, for a config written before limits were kept there, the `MemoryMax` its unit holds (`unitMemory`).
- **What a backend can make the runtime do through this,** and what it can't. It can have the runtime install the file at its recorded source and restart onto it, when that file hashes as offered, and set the memory limit and *Updates by itself*. It can't name a file to read or write, a program, an argument, a unit or an environment: nothing from an offer or a page becomes a path or a command. The programs lumiah runs (`systemctl`, `loginctl`, `getent`, `id`) are taken from `/usr/bin`, `/bin`, `/usr/sbin` and `/sbin` only, never through `PATH`; a new build is checked with the Bun that will run it, by its full path.
